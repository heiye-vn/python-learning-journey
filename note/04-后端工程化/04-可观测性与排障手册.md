# 可观测性与排障手册

可观测性的目标不是收集所有数据，而是在故障发生时快速回答：

``` text
哪里出了问题？
影响范围多大？
为什么发生？
如何恢复？
```

## 1. 信号模型

| 信号 | 回答的问题 | 示例 |
|---|---|---|
| 日志 | 事件详情 | 请求失败、异常堆栈、任务重试 |
| 指标 | 系统状态和趋势 | QPS、P95、错误率、连接数 |
| 追踪 | 请求链路 | API -> DB -> Redis -> MQ |
| 告警 | 是否需要人工处理 | 5 分钟错误率 > 5% |

先掌握日志和指标，再引入追踪。

## 2. 结构化日志

统一 JSON 格式：

``` json
{
  "timestamp": "2026-11-21T12:00:00Z",
  "level": "INFO",
  "service": "backend",
  "environment": "production",
  "request_id": "01J...",
  "user_id": "9f0...",
  "tenant_id": "3aa...",
  "method": "POST",
  "path": "/documents",
  "status_code": 201,
  "duration_ms": 128,
  "event": "request_completed"
}
```

必须记录：

- 时间戳，统一 UTC
- 服务名
- 环境名
- 请求 ID
 请求路径和状态码
 耗时
 错误码

不要记录：

- 密码
- JWT
- Cookie
- 数据库连接串
- 完整文件内容
- 身份证号等敏感数据

## 3. 中间件实现

``` python
import time
from uuid import uuid4

from fastapi import Request
import structlog


logger = structlog.get_logger()


@router.middleware("http")
async def request_logging(
    request: Request,
    call_next,
):
    request_id = request.headers.get("X-Request-ID", str(uuid4()))
    start = time.perf_counter()

    try:
        response = await call_next(request)
    except Exception:
        logger.exception(
            "request_failed",
            request_id=request_id,
            method=request.method,
            path=request.url.path,
        )
        raise

    duration_ms = round((time.perf_counter() - start) * 1000, 2)
    response.headers["X-Request-ID"] = request_id

    logger.info(
        "request_completed",
        request_id=request_id,
        method=request.method,
        path=request.url.path,
        status_code=response.status_code,
        duration_ms=duration_ms,
    )
    return response
```

生产排障时先用 `request_id` 关联日志，而不是盲目搜索整台机器日志。

## 4. Prometheus 指标

常用四类指标：

| 类型 | 用途 | 示例 |
|---|---|---|
| Counter | 只增计数 | 请求数、错误数 |
| Gauge | 可增可减 | 当前连接数、队列长度 |
| Histogram | 分布 | 延迟、文件大小 |
| Summary | 分位数 | P95 / P99 |

业务指标示例：

``` python
from prometheus_client import Counter, Gauge, Histogram


DOCUMENT_UPLOADS = Counter(
    "document_uploads_total",
    "Total document uploads",
    ["tenant_id", "result"],
)

DOCUMENT_PROCESSING_QUEUE = Gauge(
    "document_processing_queue_size",
    "Documents waiting for processing",
)

DOCUMENT_PROCESSING_SECONDS = Histogram(
    "document_processing_seconds",
    "Document processing duration",
    buckets=[0.1, 0.5, 1, 5, 10, 30, 60],
)
```

核心指标：

- HTTP QPS
- HTTP 错误率
- P95 / P99 延迟
- 数据库连接池使用率
- 数据库活跃连接
- 慢查询数
- 锁等待
- Redis 命中率
- MQ 队列长度
- Worker 失败率

## 5. Grafana

常用面板：

1. 服务健康
   - QPS
   - 错误率
   - P95 / P99
2. 数据库
   - 活跃连接
   - 连接池等待
   - 慢查询
   - 锁等待
3. Redis
   - 内存
   - 命中率
   - 拒绝连接
4. 任务
   - 队列长度
   - 处理耗时
   - 失败任务
   - 死信队列

面板应按 `service`、`environment`、`tenant` 过滤，但不要把租户数据暴露给无权限用户。

## 6. 告警

告警应该面向可行动的问题：

``` text
5 分钟错误率 > 5%
P95 延迟 > 2s 持续 10 分钟
数据库连接池等待 > 0 持续 1 分钟
队列积压 > 1000 持续 15 分钟
磁盘剩余 < 20%
备份连续失败 1 次
```

不要把正常波动都配置成告警，否则会造成告警疲劳。

## 7. 分布式追踪

基础概念：

- Trace：一次完整请求。
- Span：一次函数或远程调用。
- Context：跨服务传播上下文。

OpenTelemetry 建议：

``` python
from opentelemetry import trace


tracer = trace.get_tracer(__name__)


@router.get("/documents/{document_id}")
async def read_document(document_id: UUID):
    with tracer.start_as_current_span("load_document") as span:
        span.set_attribute("document.id", str(document_id))
        return await document_repository.get(document_id)
```

Span 属性不要包含敏感内容。

## 8. 常见故障排查

### 8.1 API 响应慢

排查顺序：

1. 看请求路径、状态码和 P95。
2. 找 `request_id` 对应日志。
3. 看数据库连接池等待。
4. 看慢查询日志。
5. 看锁等待。
6. 看外部服务耗时。
7. 看容器 CPU 和内存。

### 8.2 连接池耗尽

现象：

``` text
TimeoutError
pool timeout
too many connections
```

常见原因：

- 并发过高
- 事务太长
 请求中等待外部 API
- 连接池配置过小
- 事务未提交或回滚

处理：

``` sql
SELECT count(*), state
FROM pg_stat_activity
GROUP BY state;
```

原则：

- 事务内不要调用慢外部服务。
- 连接池上限和 PostgreSQL `max_connections` 匹配。
- 为慢 SQL 建索引或改写查询。

### 8.3 慢 SQL

``` sql
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

用 `EXPLAIN ANALYZE`：

``` sql
EXPLAIN ANALYZE
SELECT *
FROM documents
WHERE tenant_id = '...'
ORDER BY created_at DESC
LIMIT 20;
```

重点看：

- Seq Scan
 估计行数与实际行数差异
- 排序方式
- 临时文件
- 执行时间

### 8.4 锁等待

``` sql
SELECT
    blocked.pid AS blocked_pid,
    blocking.pid AS blocking_pid,
    blocked.query AS blocked_query,
    blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = any(pg_blocking_pids(blocked.pid));
```

常见原因：

- 长事务
- 迁移锁表
- 高并发更新同一行
 事务中调用外部服务

### 8.5 队列积压

检查：

- 队列长度
- 消费者数量
- Worker CPU / 内存
- 任务失败率
- 死信队列
- 重试风暴

处理优先级：

1. 扩消费者。
2. 降低发布速度。
3. 修复失败任务。
4. 处理死信。
5. 恢复正常流量。

## 9. 故障响应模板

``` text
时间：
现象：
影响范围：
当前状态：
已执行动作：
根因假设：
需要的支持：
下次更新时间：
```

先恢复服务，再做完整根因分析。恢复过程中不要引入未经验证的变更。

## 10. 阶段练习

### 练习 1：结构化日志

给 API 添加请求日志。

验收：

- 每个请求有唯一 ID。
- 响应头返回请求 ID。
- 日志包含方法、路径、状态码和耗时。
- 日志没有敏感信息。

### 练习 2：核心指标

接入 Prometheus。

验收：
- 能看到 QPS。
- 能看到错误率。
- 能看到延迟分布。

### 练习 3：故障演练

制造一个慢查询。

验收：
- Grafana 能看到 P95 上升。
- 能定位慢 SQL。
- 能通过索引或 SQL 改写恢复。
