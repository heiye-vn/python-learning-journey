# 备份恢复与零停机变更

备份的价值不在于备份文件是否生成，而在于故障时能否按目标时间恢复数据。本文覆盖 PostgreSQL 备份恢复、Alembic 迁移规范和零停机变更。

## 1. 备份目标

先回答四个问题：

1. 可接受丢失多少数据？
2. 最长允许多长时间恢复？
3. 是否需要恢复到历史某个时间点？
4. 备份是否存放在异地？

常见指标：

- RPO：Recovery Point Objective，最多丢多少数据。
- RTO：Recovery Time Objective，多久能恢复。

示例：

``` text
RPO = 5 分钟
RTO = 1 小时
```

如果 RPO 要求 5 分钟，仅每天一次 `pg_dump` 无法满足。

## 2. PostgreSQL 备份方式

| 方式 | 适用场景 | RPO |
|---|---|---|
| SQL dump | 小项目、开发环境 | 取决于备份频率 |
| 文件级备份 | 中小项目 | 取决于备份频率 |
| WAL 归档 + 基础备份 | 生产 | 可到秒级或事务级 |

### 2.1 pg_dump

``` bash
pg_dump \
  --format=custom \
  --file=app-$(date +%F-%H%M).dump \
  --dbname=app
```

恢复：

``` bash
createdb app_restored
pg_restore --dbname=app_restored app-2026-11-21-0100.dump
```

优点是简单。缺点是不能做 PITR，只适合数据量较小或恢复要求不高的系统。

### 2.2 WAL 归档

`postgresql.conf`：

``` ini
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
wal_level = replica
max_wal_senders = 3
```

基础备份：

``` bash
pg_basebackup \
  --pgdata=/backup/base \
  --format=tar \
  --wal-method=stream \
  --checkpoint=fast
```

WAL 归档配合基础备份，可以将数据库恢复到指定时间点。

## 3. 备份策略

推荐：

``` text
每日基础备份 + 持续 WAL 归档 + 异地保存 + 每月恢复演练
```

检查清单：

- 备份成功有告警。
- 备份失败有告警。
- 备份文件可读。
 恢复演练已执行。
- 备份权限最小化。
- 备份存储加密。
- 备份保留策略明确。
- 备份不和工作数据放在同一磁盘。

## 4. 恢复演练

只验证“备份文件存在”没有意义，必须验证可恢复。

### 4.1 恢复到新库

``` bash
createdb app_verify
pg_restore --dbname=app_verify app-2026-11-21-0100.dump
```

### 4.2 数据验证

``` sql
SELECT count(*) FROM tenants;
SELECT count(*) FROM users;
SELECT max(created_at) FROM documents;
```

再运行应用只读查询，确认结构可访问。

### 4.3 PITR 示例

``` text
1. 停止恢复实例
2. 准备基础备份
3. 创建 recovery.signal
4. 配置 restore_command
5. 设置 recovery_target_time
6. 启动 PostgreSQL
7. 验证数据
8. 执行 promote
```

恢复目标时间必须早于误操作时间。

## 5. Alembic 迁移规范

### 5.1 目录

``` text
alembic/
├── env.py
├── script.py.mako
└── versions/
    ├── 20261121_0001_create_tenants.py
    └── 20261121_0002_create_documents.py
```

### 5.2 迁移文件

``` python
def upgrade() -> None:
    op.create_table(
        "documents",
        sa.Column("id", postgresql.UUID(as_uuid=True), primary_key=True),
        sa.Column("tenant_id", postgresql.UUID(as_uuid=True), nullable=False),
        sa.Column("title", sa.Text(), nullable=False),
        sa.Column("sha256", postgresql.Bytea(), nullable=False),
    )


def downgrade() -> None:
    op.drop_table("documents")
```

规则：

- 一个迁移只做一件事。
- 迁移必须可测试。
- 不要删除已有迁移。
 不要修改已被生产执行过的迁移。
- 自动生成后必须人工检查。
- 迁移里不要写入环境差异配置。

## 6. 零停机建索引

普通建索引会锁表：

``` sql
CREATE INDEX idx_documents_tenant_created
ON documents (tenant_id, created_at DESC);
```

生产使用：

``` sql
CREATE INDEX CONCURRENTLY idx_documents_tenant_created
ON documents (tenant_id, created_at DESC);
```

注意：

| 特性 | 普通索引 | 并发索引 |
|---|---|---|
| 阻塞写入 | 是 | 通常不阻塞 |
| 事务 | 可在事务中 | 不能在事务中 |
| 失败状态 | 少 | 可能留下 INVALID |
| 耗时 | 较短 | 较长 |

确认索引：

``` sql
SELECT indexrelid::regclass, indisvalid
FROM pg_index
WHERE indexrelid::regclass::text = 'idx_documents_tenant_created';
```

失败后删除无效索引再重建。

## 7. 兼容式表结构变更

### 7.1 删除字段

正确顺序：

``` text
1. 新代码停止读写该字段
2. 确认无依赖
3. 后续版本删除字段
```

不要发布代码和删除字段同时进行。

### 7.2 重命名字段

``` text
1. 添加新字段
2. 迁移历史数据
3. 代码双读双写
4. 灰度验证
5. 只写新字段
6. 删除旧字段
```

### 7.3 修改类型

常见做法：

``` text
1. 新增新类型字段
2. 用后台任务回填
3. 校验一致
4. 切换读写
5. 删除旧字段
```

不要一次性修改有大量历史数据的列类型。

## 8. 回滚方案

| 变更类型 | 回滚方式 |
|---|---|
| 纯代码 | 回滚镜像 |
| 新增字段 | 保留字段，代码回滚 |
| 删除字段 | 恢复备份或前滚 |
| 建索引 | 删除索引 |
| 重命名字段 | 回切旧字段 |
| 数据回填 | 停止任务并修复 |

上线前明确：

``` text
可以回滚：
需要多长时间：
数据是否会受影响：
谁执行：
如何验证恢复成功：
```

## 9. 变更清单

- 变更目的明确
- 已在 staging 验证
- 备份已完成
- 迁移可回滚或可前滚
- 建索引使用 `CONCURRENTLY`
- 灰度计划已准备
- 监控面板已打开
- 回滚负责人已确定
- 通知相关团队
- 变更窗口避开业务高峰

## 10. 阶段练习

### 练习 1：备份与恢复

执行：

``` text
pg_dump -> 删除测试库 -> 恢复 -> 数据校验
```

验收：

- 恢复后的行数一致。
- 外键约束有效。
- 应用可连接。

### 练习 2：并发索引

在测试表上执行：

``` sql
CREATE INDEX CONCURRENTLY ...
```

验收：

- 索引有效。
- 能通过 `pg_index.indisvalid` 验证。

### 练习 3：零停机删字段

模拟：

``` text
发布兼容代码 -> 停止使用字段 -> 后续删除字段
```

验收：

 第一次发布不破坏旧版本回滚。
 第二次发布后才删除字段。
