# 02｜文件指纹去重：PostgreSQL + 对象存储 + 并发幂等

## 1. 业务问题拆解

文件去重通常包含三个不同实体： 1. 物理文件对象：实际存储在 S3
兼容对象存储中的 Blob。 2. 文件元数据：哈希、大小、MIME、存储
Key、解析状态。 3.
业务引用：哪个用户、租户、知识库或文档版本引用了该物理文件。

不要把"文件内容相同"和"业务文档相同"混为一谈。同一个物理文件可能被多个知识库或多个业务记录引用。

## 2. SHA-256 计算

SHA-256 输出 256 bit，即 32 字节。常见存储选择： - `BYTEA`：存原始 32
字节，空间紧凑。 - `CHAR(64)` / `TEXT`：存 64
位十六进制字符串，易读但占用更大。

Python 流式计算，避免把大文件整体读入内存：

``` python
import hashlib

def sha256_file(file_obj, chunk_size=1024 * 1024) -> bytes:
    digest = hashlib.sha256()
    while chunk := file_obj.read(chunk_size):
        digest.update(chunk)
    return digest.digest()  # 32 bytes
```

如果使用十六进制：

``` python
hex_digest = digest.hexdigest()  # 64 chars
```

## 3. 表结构示例

``` sql
CREATE TABLE file_blobs (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sha256 BYTEA NOT NULL,
    byte_size BIGINT NOT NULL CHECK (byte_size >= 0),
    storage_key TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK (octet_length(sha256) = 32),
    UNIQUE (sha256)
);

CREATE TABLE document_assets (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    blob_id BIGINT NOT NULL REFERENCES file_blobs(id),
    original_name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

如需租户隔离去重，可将唯一约束设计为
`(tenant_id, sha256)`，但这通常意味着 Blob
元数据也要按租户建模。先确定产品语义，再确定唯一键。

## 4. 并发安全：不要只做先查再插

不安全的逻辑：

``` text
请求 A：SELECT 不存在
请求 B：SELECT 不存在
请求 A：INSERT
请求 B：INSERT
```

两个请求可能同时通过查询。应由唯一约束承担最终仲裁。

``` sql
INSERT INTO file_blobs (sha256, byte_size, storage_key)
VALUES ($1, $2, $3)
ON CONFLICT (sha256) DO NOTHING
RETURNING id;
```

如果没有返回行，再查询已存在记录：

``` sql
SELECT id, storage_key
FROM file_blobs
WHERE sha256 = $1;
```

也可使用 `ON CONFLICT ... DO UPDATE ... RETURNING`，但不要为了拿到 ID
而无意义地更新行；无意义 UPDATE 会制造新版本、WAL
和膨胀压力。根据并发语义选择合适模式。

## 5. 对象存储与数据库一致性

对象存储和 PostgreSQL 通常不共享一个 ACID 事务。常见稳健流程： 1.
上传到临时对象 Key。 2. 计算哈希并完成文件校验。 3.
在数据库事务中尝试登记 Blob 和业务引用。 4.
若发现重复，丢弃临时对象，复用已存在 Blob。 5.
若登记失败，保留可重试状态或安排清理任务。 6.
定期扫描孤儿对象和缺失对象，执行补偿。

不要在数据库事务中长时间等待大文件上传；事务应尽量短。

更完整的对象生命周期可以使用状态机表达：

``` text
INIT -> UPLOADING -> OBJECT_READY -> METADATA_READY -> PROCESSING -> READY
```

失败状态包括 `UPLOAD_FAILED`、`METADATA_FAILED`、`PROCESS_FAILED`。
系统需要超时扫描、补偿任务和孤儿对象清理。

对象 Key 可由指纹派生，例如：

``` text
blobs/sha256/ab/cd/<完整摘要>
```

相同摘要指向同一逻辑对象位置，但要确认对象存储支持条件写入或防覆盖，
并考虑临时对象转正式对象、租户命名空间和对象完整性校验。

删除逻辑文档不等于立即删除物理 Blob。应检查是否仍有有效引用，并通过
异步回收、软删除、保留期和并发引用创建控制风险。引用计数更新必须放在
数据库事务或可靠事件处理机制中。

## 6. 幂等任务设计

对上传、解析、切片、向量化任务设置业务幂等键，例如：
`blob_id + parser_version + pipeline_version + embedding_model_version`。

同一文件使用不同解析器版本或 Embedding 模型时，可能需要重新处理。
解析任务表建议包含：

-   `task_id`
-   `idempotency_key`（唯一）
-   `status`
-   `attempt_count`
-   `lease_until` 或锁租约
-   `last_error`
-   `created_at` / `updated_at`

任务表可有唯一约束：

``` sql
CREATE UNIQUE INDEX uk_parse_job_idempotency
ON parse_jobs (tenant_id, document_version_id, pipeline_version);
```

消费者可能收到重复消息，因此必须允许重复投递，并通过数据库唯一约束、状态机或幂等记录确保副作用不会重复执行。

## 7. 哈希碰撞与安全边界

SHA-256
碰撞在正常业务中极难，但哈希不是数学意义上对任意输入的绝对唯一证明。高价值场景可在哈希相同后进一步比较文件大小，必要时做内容校验。不要使用
MD5 作为对抗性安全场景的完整性依据。

文件大小相同不代表内容相同。最终策略应与风险等级、性能成本和合规要求匹配。

## 8. 安全与治理

-   校验文件大小、扩展名、真实 MIME 类型和文件签名。
-   防止路径穿越，不使用用户文件名直接拼接对象路径。
-   对压缩包和 Office 文档防 ZIP Bomb。
-   扫描恶意文件，限制解析器 CPU、内存和执行时间。
-   下载和预览必须重新鉴权。
-   避免通过接口响应暴露跨租户文件是否存在。
-   日志不要输出敏感文件内容或完整访问凭证。
-   处理文件版本、审核、删除和保留策略。

## 9. 验收测试

-   [ ] 同一文件并发上传 100 次，数据库只登记一个 Blob。
-   [ ] 不同租户上传同一文件，结果符合租户隔离策略。
-   [ ] 上传对象成功但数据库失败，补偿机制可处理。
-   [ ] 数据库登记成功但消息发布失败，Outbox 或重试能恢复。
-   [ ] 消息重复投递不会重复切片或重复创建向量。
-   [ ] 删除某个业务引用不会误删仍被其他业务引用的物理文件。
